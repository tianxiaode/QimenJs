## 架构改进方案：expose(host) 简化 Ability 继承

### 问题分析

当前 Ability 继承门槛过高的根本原因：**`expose(proxy)` 在预编译阶段调用，此时宿主还不存在，所以 `proxy.host` 是一个延迟绑定的 getter，框架需要在运行时做大量临时切换 hack**。

这导致了：
1. **访问宿主的方式混乱**：`proxy.host`（hostRef 闭包）、`this`（bind 到宿主）、`this.host`（ComposableBase getter）、`proxy.self.host`（反模式）四种方式混用
2. **私有状态存储复杂**：需要 `getOrCreateState()` + `proxy.self.getXxxState()` 的间接调用模式
3. **框架内部 hack 多**：getter/setter/方法调用时临时切换 `sharedHostRef` 和 `ability.host`，`createDisposer` 中恢复原值
4. **expose() 有隐含禁区**：不能在函数体中直接用 `proxy.host`，但没有编译期检查

### 方案：expose(host) — 在 factory 调用时执行 expose

**核心思路**：将 `expose()` 的调用时机从"预编译阶段"推迟到"factory(host) 调用阶段"。此时宿主已经确定，`expose(host)` 可以直接拿到宿主引用。

#### 当前流程

```
precompile() 阶段（无宿主）：
  1. 创建 proxy（proxy.host = getter from sharedHostRef）
  2. 调用 expose(proxy) → 得到 props
  3. 为每个 prop 创建 DescriptorFactoryFn
  4. factory(host) 调用时：创建 hostRef，临时切换 sharedHostRef，执行 getter/setter

问题：expose() 在无宿主时调用，proxy.host 是延迟绑定，需要运行时 hack
```

#### 新流程

```
precompile() 阶段（无宿主）：
  1. 记录 ability 实例（不调用 expose）

factory(host) 调用阶段（有宿主）：
  1. 调用 expose(host) → 得到 props（host 直接可用）
  2. 为每个 prop 创建 PropertyDescriptor（闭包直接捕获 host）
  3. 不需要 hostRef 切换 hack
```

#### 新的 expose 签名

```typescript
// 之前
protected abstract expose(proxy: AbilityProxy): IExposeResult;
// proxy.host 是 getter，延迟绑定，需要 hostRef hack

// 之后
protected abstract expose(host: THost): IExposeResult;
// host 直接可用，闭包直接捕获，无需 hack
```

#### 新的 Ability 写法对比

```typescript
// ===== 之前（复杂）=====
class CounterAbility extends AbilityBase {
    private getCountState() {
        return this.getOrCreateState(() => ({ count: 0 }));
    }
    protected expose(proxy: AbilityProxy): IExposeResult {
        return {
            count: { get: () => proxy.self.getCountState().count },
            increment: function() { proxy.self.getCountState().count++; },
        };
    }
}

// ===== 之后（简单）=====
class CounterAbility extends AbilityBase {
    protected expose(host: any): IExposeResult {
        const state = { count: 0 };  // 直接在闭包中创建 per-host 状态
        return {
            count: { get: () => state.count },
            increment() { state.count++; },  // 方法直接写，this 自动 bind 到 host
        };
    }
}
```

#### 关键优势

| 维度 | 之前（expose(proxy)） | 之后（expose(host)） |
|------|----------------------|---------------------|
| 宿主访问 | `proxy.host`（延迟 getter） | `host`（直接参数） |
| 私有状态 | `getOrCreateState()` + `proxy.self.getXxxState()` | 闭包变量（自然隔离） |
| 框架 hack | sharedHostRef 临时切换、ability.host 临时切换 | 不需要 |
| expose() 禁区 | 不能在函数体中用 proxy.host | 无禁区 |
| 方法中 this | bind 到宿主，this.host 返回宿主 | 同上（不变） |
| onDispose | 需要临时设置 ability.host | host 可通过闭包或参数传入 |

#### 需要解决的问题

1. **性能**：expose() 从"预编译时调用一次"变为"每个宿主调用一次"。需要评估是否可接受。
   - 当前 30 个 Ability 的 expose() 都是轻量级（返回对象字面量），性能影响可忽略
   - 如果有重计算，可以在 expose() 内部做缓存

2. **缓存策略**：当前 `DescriptorFactoryFn` 缓存的是"工厂函数"，新方案缓存什么？
   - 方案 A：不再缓存 descriptor，每次 factory 调用都执行 expose(host)
   - 方案 B：缓存 expose() 返回的 props 结构描述，factory 时只做闭包绑定
   - 推荐方案 A（简单直接，性能可接受）

3. **onDispose 如何获取 host**：
   - 方案 A：onDispose(host) 参数传入
   - 方案 B：factory 阶段创建闭包，onDispose 通过闭包访问 host
   - 推荐方案 A（显式参数，更清晰）

4. **DebounceAbilityBase 适配**：
   - 当前 `getDebouncedAction()` 在 expose() 中调用，依赖 `this`（Ability 实例）
   - 新方案中 expose(host) 的 this 仍然是 Ability 实例，所以 `this.getDebouncedAction()` 仍可用
   - 但防抖函数的 per-host 隔离可以简化：每个 host 调用 expose() 时创建独立的防抖 Map

5. **向后兼容**：
   - expose(proxy) → expose(host) 是破坏性变更
   - 需要同时修改所有 30 个 Ability 子类
   - 可以分步进行：先支持两种签名，再逐步迁移
