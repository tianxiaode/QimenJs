## 主要完成

### 1. AbilityBase `this` 绑定问题彻底修复

**问题**：`AbilityBase.precompile()` 创建临时实例调用 `expose()`，闭包中的 `this` 指向临时实例而非真正的 Ability 实例。箭头函数的 `this` 是词法绑定，`call()`/`bind()`/`apply()` 均无法改变。这导致所有 Ability 闭包中 `this.host` 始终为 `null`，是系统性 bug。

**解决方案**：引入 `AbilityProxy` 代理对象，彻底绕开 `this` 指向问题。

| 机制 | 说明 |
|------|------|
| `AbilityProxy` 接口 | `{ host: THost, self: TSelf }`，`host` 为宿主，`self` 为 Ability 实例 |
| `expose(proxy)` | 子类实现，闭包通过 `proxy.host`/`proxy.self` 访问，不依赖 `this` |
| `proxy.host` getter | 从 `sharedHostRef` 读取值，支持多实例隔离 |
| getter/setter | 执行时临时切换 `sharedHostRef`，确保多宿主实例互不干扰 |
| 方法 | `bind(host)` 绑定，`this` 就是宿主，`this.host` 通过 ComposableBase getter 返回宿主自身 |
| `ComposableBase.host` getter | `get host() { return this; }`，统一 getter/setter 和方法中的宿主访问写法 |

**访问规则**：

| 场景 | 宿主访问 | Ability 私有属性 |
|------|----------|-----------------|
| getter/setter | `proxy.host` | `proxy.self._xxx` |
| 方法（普通函数） | `this.host`（ComposableBase getter） | `proxy.self._xxx` |
| 方法（箭头函数） | `proxy.host` | `proxy.self._xxx` |

### 5. `schemaKey` → 直接引用 Schema 对象

**问题**：`schemaKey: string` 是运行时弱关联，拼错不报错，IDE 无法跳转/重构。

**解决方案**：Manager 直接引用 Schema 对象，自动注册到 SchemaRegistrar。

| 改动 | 说明 |
|------|------|
| `CoreEntityManager.schemaKey: string` | → `abstract schema: RegistrSchema` |
| `CoreEntityManager.get schema()` | → `get compiledSchema()`，自动注册 + 延迟编译 |
| `ICoreEntityManager.schemaKey` | → `schema: RegistrSchema` |
| `ICoreEntityManager.readonly schema` | → `readonly compiledSchema: Schema` |
| `SchemaAbility` | `host.schemaKey` → `host.schema.name`，自动注册 |
| `LocalGetAbility` | `host.schema.idField` → `host.compiledSchema.idField` |

**业务层用法对比**：

```typescript
// 之前：字符串 key，无编译时检查
SchemaRegistrar.register({ name: 'User', fields: [...] });
class UserManager extends RemoteCrudEntityManager {
    schemaKey = 'User';
}

// 现在：直接引用，有类型检查，自动注册
const UserSchema: FlatSchema = { name: 'User', fields: [...] };
class UserManager extends RemoteCrudEntityManager {
    schema = UserSchema;
}
```

**灵活性**：支持三种组织方式——
1. 集中定义分散引用（schemas/ 目录统一管理）
2. 就地定义（Manager 内部直接写 Schema）
3. 混合（共享基础 Schema 集中定义，业务 Schema 就地定义）

### 12. 防抖架构三层调整

**问题**：防抖覆盖不完整，策略不统一，TreeManagerAbility 空继承，DOM 事件层声明未实现。

**解决方案**：建立三层防抖体系——

| 层级 | 位置 | 策略 | 改动 |
|------|------|------|------|
| DOM 事件层 | `DomEventAdapter.bind()` | 防抖/节流配置 | `BindOptions` 新增 `debounce`/`throttle`，`bind()` 中对 gesture callback 应用 |
| Manager 层 | Ability | 读操作防抖，写操作 loading 锁 | `RemoteDeleteAbility` 加 loading 锁；`TreeManagerAbility` 实际使用防抖 |
| State 层 | `commitChange()` | 视图刷新防抖 | `refreshView` 调用改为 50ms 防抖，`setCache` 保持即时 |

**防抖策略**：

| 操作类型 | 策略 | 说明 |
|----------|------|------|
| 读操作（list/getAll/expand/refresh） | 防抖 | 合并短时间内的多次调用 |
| 写操作（create/update/delete） | loading 锁 | 拒绝并发，不合并 |
| toggle | leading 防抖 | 首次立即执行 + 乐观更新 |
| save（本地批量提交） | trailing 防抖 | 延迟执行，合并多次变更 |
| 视图刷新（refreshView） | 50ms 防抖 | 高频数据变更时合并渲染 |
| DOM 事件 | 用户可配置 | 防抖或节流，第一道防线 |

**TreeManagerAbility 防抖**：
- `expand`: 200ms leading（快速展开多节点时合并，首次立即响应）
- `refresh`: 300ms leading（快速刷新多父节点时合并）

### 2. Ability 实例共享问题

`ComposableRegistrar` 缓存了 Ability 实例，所有宿主实例共享同一个 Ability 实例。这意味着：
- Ability 的私有属性（如 `_changes`、`_deleteSnapshots`）在多个宿主实例间共享
- `ability.host` 在多实例场景下不稳定
- 当前通过 `hostRef` 闭包隔离解决了 getter/setter 的多实例问题，但 Ability 私有方法仍依赖 `this.host`

**可能的解决方案**：
- 每个宿主实例创建独立的 Ability 实例（放弃缓存）
- Ability 私有方法全部通过参数接收 host（当前部分已实现）

### 3. FlatRemoteStateAbility.expose() 违反 proxy 访问规则

**问题**：`FlatRemoteStateAbility.expose()` 和 `FlatRemoteQueryAbility.expose()` 在函数体中直接访问 `proxy.host.state`，违反了 `AbilityBase` 文档中的规则——"只能在返回的 getter/setter/方法（闭包）中使用 proxy，不能在 expose() 函数体中直接使用（此时 proxy.host 尚未设置）"。

**影响**：当 State 类被 standalone 实例化（不在 Manager 上下文中）时，`precompile()` 阶段 `proxy.host` 为 `null`，导致 `TypeError: Cannot read properties of null (reading 'state')`。

**当前规避**：测试中通过 `jest.mock` 替换 `FlatRemoteStateAbility`，将 `proxy.host.state` 的访问延迟到闭包中。

**根本修复**：应修改源码中 `FlatRemoteStateAbility` 和 `FlatRemoteQueryAbility`，将 `const state = proxy.host.state;` 移入各 getter/方法闭包内部。

### 4. StateDirtyAbility.isDirty() 在 dispose 后不可调用

**问题**：`StateDirtyAbility.isDirty()` 函数体开头就执行 `const idField = this.schema.idField || 'id';`，即使无参调用也会访问 `this.schema`。而 `BaseEntityState.dispose()` 将 `schema` 设为 `null`，导致 dispose 后调用 `isDirty()` 抛出 `TypeError`。

**修复建议**：将 `idField` 的提取移到 `if (!item)` 检查之后，无参调用时直接返回 `_snapshots.size > 0`，不需要访问 schema。
