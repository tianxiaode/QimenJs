### 2. Token 管理方案设计与实现 ✅

#### 2.1 架构讨论过程

经过深入的架构讨论，我们否定了多个复杂方案：

**方案 1：TokenService + TokenInjector**
- ❌ 问题：违反单一职责原则
- ❌ 问题：Token 获取和注入耦合

**方案 2：TokenProvider 接口**
- ❌ 问题：循环依赖（auth ↔ http）
- ❌ 问题：Provider 变得复杂

**方案 3：AuthInjectorRegistry**
- ❌ 问题：实例管理复杂
- ❌ 问题：刷新流程啰嗦

**最终方案：极简设计**
- ✅ Token 存储在 DomainConfig
- ✅ DomainRegistrar 提供批量更新方法
- ✅ TokenInjector 根据 authInjector 配置注入
- ✅ 应用层完全控制 token 的获取和刷新

#### 2.2 实现细节

**DomainConfig 新增字段**:
```typescript
interface DomainConfig {
    // ... 其他配置
    token?: string;  // Token 存储
    authInjector?: 'bearer' | 'basic' | ((context) => void);  // 注入器
}
```

**DomainRegistrar 新增方法**:
```typescript
// 批量更新 token
updateToken(token: string, ...domains: string[]): void;

// 批量清除 token
clearToken(...domains: string[]): void;
```

**TokenInjector 处理器**:
- 支持 'bearer' 和 'basic' 预定义方式
- 支持自定义函数，传入 RequestContext
- 完全灵活，可以修改 headers、queryParams 等

**修改的文件**:
- `src/registry/types.ts` - 添加 token 和 authInjector 字段
- `src/registry/registrars/DomainRegistrar.ts` - 添加 updateToken 和 clearToken 方法

## 技术决策

### 1. 纯粹的职责分离
- HTTP 包只负责 HTTP 通信
- Entity 包只负责数据处理
- 不再混合在一起

### 2. 统一的上下文
- 使用 RequestContext 作为统一上下文
- 所有处理器都操作同一个上下文

### 3. 自动注册机制
- actions 在模块加载时自动注册
- 无需手动调用注册函数

### 4. 简化的 API
- 移除不必要的复杂性
- 只提供必要的功能

### 5. Token 管理的极简设计
- Token 存储在 DomainConfig
- 不需要额外的接口和注册器
- 应用层完全控制获取和刷新

## HTTP Actions 管道流程

```
1. PREPARE (准备阶段 - 100)
   └─ TokenInjector (Token 注入)
   └─ CommonParamsEnricher (合并公共参数)
   └─ UrlBuilder (构建 URL)

2. EXCHANGE (交换阶段 - 200)
   └─ FetchTransport (Fetch 传输)
   └─ XhrTransport (XHR 传输)

3. PROCESS (处理阶段 - 300)
   └─ ResponseAnalyzer (响应分析)
   └─ DataParser (数据解析 - raw → JSON)

4. ALIGN (对齐阶段 - 400)
   └─ DownloadInterceptor (下载拦截)
```
