### 1. FlatRemoteStateAbility/FlatRemoteQueryAbility/TreeRemoteStateAbility expose() 修复

**问题**：`FlatRemoteStateAbility.expose()` 和 `FlatRemoteQueryAbility.expose()` 在函数体中直接访问 `proxy.host.state`，违反了 AbilityBase 文档中的规则——"只能在返回的 getter/setter/方法（闭包）中使用 proxy，不能在 expose() 函数体中直接使用（此时 proxy.host 尚未设置）"。`TreeRemoteStateAbility` 也有同样问题。

**影响**：当 State 类被 standalone 实例化（不在 Manager 上下文中）时，`precompile()` 阶段 `proxy.host` 为 `null`，导致 `TypeError: Cannot read properties of null`。

**解决方案**：将 `const state = proxy.host.state` / `const host = proxy.host` 的访问移入各 getter/方法闭包内部。

| 文件 | 修改 |
|------|------|
| FlatRemoteStateAbility.ts | `const state = proxy.host.state` → 每个闭包内 `proxy.host.state.xxx` |
| FlatRemoteQueryAbility.ts | `const host = proxy.host; const state = host.state` → 每个闭包内 `const host = proxy.host; const state = host.state` |
| TreeRemoteStateAbility.ts | `const state = proxy.host.state` → 每个闭包内 `proxy.host.state.xxx` |

### 2. StateDirtyAbility.isDirty() dispose 后不可调用修复

**问题**：`isDirty()` 函数体开头就执行 `const idField = this.schema.idField || 'id'`，即使无参调用也会访问 `this.schema`。而 `BaseEntityState.dispose()` 将 `schema` 设为 `null`，导致 dispose 后调用 `isDirty()` 抛出 `TypeError`。

**解决方案**：将 `idField` 的提取移到 `if (!item)` 检查之后，无参调用时直接返回 `_snapshots.size > 0`，不需要访问 schema。

```typescript
// 修改前
isDirty: function(this: IBaseEntityState, item?: any): boolean {
    const idField = this.schema.idField || 'id';
    if (!item) return proxy.self._snapshots.size > 0;
    // ...
}

// 修改后
isDirty: function(this: IBaseEntityState, item?: any): boolean {
    if (!item) return proxy.self._snapshots.size > 0;
    const idField = this.schema.idField || 'id';
    // ...
}
```

### 5. FlatRemoteStateAbility/TreeRemoteStateAbility 从 State 迁移到 Manager

**问题**：`FlatRemoteStateAbility` 和 `TreeRemoteStateAbility` 按命名规范属于 Manager 层能力（将 `state` 属性代理到 Manager 实例上），但被错误地声明在 State 类的 `abilities` 中。这导致 standalone 实例化 State 时，这些 Ability 的 getter 覆盖了 State 自身的数据属性（如 `loading`、`items`、`page`），导致构造函数赋值失败。

**解决方案**：

| 文件 | 改动 |
|------|------|
| `FlatRemoteEntityState.ts` | 从 `abilities` 移除 `FlatRemoteStateAbility`，移除相关 import 和类型引用 |
| `TreeRemoteEntityState.ts` | 从 `abilities` 移除 `TreeRemoteStateAbility`，移除相关 import 和类型引用 |
| `managers.ts` | `RemoteReadonlyEntityManager`/`RemoteCrudEntityManager` 添加 `FlatRemoteStateAbility`；`RemoteTreeEntityManager` 添加 `TreeRemoteStateAbility` |
| `FlatRemoteEntityState.test.ts` | 移除 `FlatRemoteStateAbility` 的 `jest.mock` |
| `TreeRemoteEntityState.test.ts` | 移除 `TreeRemoteStateAbility` 的 `jest.mock` |

**效果**：State 类 standalone 实例化不再被 Manager Ability 的 getter 覆盖数据属性，测试不再需要 mock。

### 6. Ability 实例共享问题评估

**问题**：`ComposableRegistrar` 缓存 Ability 实例，所有宿主共享同一个 Ability 实例，导致：
- 私有属性（`_changes`、`_deleteSnapshots`、`_snapshots`）在多宿主间共享
- `ability.host` 在多实例下不稳定
- `onDispose` 清理会影响其他宿主

**当前缓解**：
- hostRef 闭包隔离 getter/setter 的多实例访问
- 方法 bind 到宿主，`this.host` 返回宿主自身

**推荐方案**：方案 C（WeakMap Per-Host State）

在 `AbilityBase` 中增加 `WeakMap<object, Map<string, any>>`，以宿主为 key 存储每个宿主的独立状态：

```typescript
// AbilityBase.ts 新增
private hostStates = new WeakMap<object, Map<string | symbol, any>>();

protected getHostState(host: object, key: string | symbol): any { ... }
protected setHostState(host: object, key: string | symbol, value: any): void { ... }
protected clearHostStates(host: object): void { ... }
```

**优点**：
- WeakMap 自动处理宿主 GC，不会内存泄漏
- 不影响预编译缓存机制
- onDispose 时只清理对应宿主的状态
- 渐进式迁移，可逐个 Ability 改造
