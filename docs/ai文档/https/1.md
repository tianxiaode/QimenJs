你这个问题已经**不是“怎么用 HttpClient”**了，而是在问 **HTTP 基础设施该怎么“抽象到位但不过度”**。
结论先给，然后一层一层拆。

---

## 先给结论（直接可落地）

### 1️⃣ **Transport（Fetch / XHR / Node）不应该“自动切换”**

👉 **应该在「应用启动阶段」显式选择 / 注入**

### 2️⃣ **认证不应该写死在 HttpClient**

👉 **用「可组合的 AuthProvider / Middleware」，启动时按系统装配**

### 3️⃣ **HttpClient = 已装配完成的“请求管道”**

👉 **一旦实例化，它就不再负责判断环境 or 业务差异**

---

## 一、为什么「自动切换 Fetch / XHR」反而是个坑？

你直觉里会觉得：

> “HttpClient 应该智能点，自动判断用 fetch 还是 ajax”

但在**工程实践里，这通常是反模式**。

### 🚨 自动切换的问题

#### ❌ 1. 运行期不可预测

```ts
if (window.fetch) useFetch()
else useXhr()
```

* polyfill / mock 会改变行为
* SSR / Edge / Worker 环境判断复杂
* 调试时你很难知道 **当前到底用的是什么**

#### ❌ 2. 能力差异被“抹平”

* fetch

  * stream
  * abort
  * no progress
* xhr

  * progress
  * sync（node 不支持）

👉 自动切换 = **只能用两者的交集能力**

#### ❌ 3. transport 是“基础设施决策”，不是业务决策

这类决策应该发生在：

> **应用启动 / 构建 / 运行环境确定时**

而不是每次 request。

---

## 二、正确的 Transport 设计方式（你现在其实已经走对了）

你现在有：

```
transport/
  ├── FetchTransport
  ├── XhrTransport
  └── HttpTransport (interface)
```

这是 **非常标准、非常正确** 的设计。

### 推荐使用方式

```ts
// bootstrap/http.ts
import { HttpClient } from '@/http'
import { FetchTransport } from '@/http/transport'

export const httpClient = new HttpClient({
  transport: new FetchTransport(),
})
```

在 **Node / SSR**：

```ts
import { NodeFetchTransport } from '@/http/transport'

export const httpClient = new HttpClient({
  transport: new NodeFetchTransport(),
})
```

📌 **结论**：

> transport 是「部署维度」的选择，而不是「请求维度」

## 三、认证问题才是你真正的痛点（你说得非常对）

> 不同系统的认证用法不同（尤其后端请求）

这句话 **100% 命中真实项目痛点**。

## 四、Auth 不该是 Middleware，而该是「策略 + 中间件」

### ❌ 常见错误设计

```ts
new AuthMiddleware({
  type: 'jwt',
  token: xxx,
})
```

问题：

* 和业务系统强耦合
* 后端、第三方、内部系统混在一起
* middleware 越写越多 if/else

---

## 五、推荐的 Auth 设计（重点）

### 1️⃣ 抽象 AuthProvider（不是 Middleware）

```ts
export interface AuthProvider {
  apply(req: HttpRequest): Promise<HttpRequest> | HttpRequest
}
```

### 2️⃣ Middleware 只是“执行者”

```ts
export class AuthMiddleware implements HttpMiddleware {
  constructor(private provider: AuthProvider) {}

  async handle(req, next) {
    const authedReq = await this.provider.apply(req)
    return next(authedReq)
  }
}
```

---

## 六、不同系统 = 不同 AuthProvider

### 示例一：前端 JWT

```ts
class JwtAuthProvider implements AuthProvider {
  apply(req: HttpRequest) {
    return req.withHeader(
      'Authorization',
      `Bearer ${getToken()}`
    )
  }
}
```

### 示例二：后端内部系统（签名）

```ts
class SignatureAuthProvider implements AuthProvider {
  apply(req: HttpRequest) {
    const signature = sign(req.url, req.body)
    return req.withHeaders({
      'X-App-Id': APP_ID,
      'X-Signature': signature,
    })
  }
}
```

### 示例三：无认证（第三方）

```ts
class NoAuthProvider implements AuthProvider {
  apply(req) {
    return req
  }
}
```

## 七、在「应用启动时」装配，而不是写死

你刚才问的这个点是**关键中的关键**：

> 要在应用启动的时候定义好才实例化或者更好配置？

**答案：是的，而且这是最佳实践。**

```ts
// bootstrap/http.ts
const authProvider =
  env === 'internal'
    ? new SignatureAuthProvider()
    : env === 'frontend'
    ? new JwtAuthProvider()
    : new NoAuthProvider()

export const httpClient = new HttpClient({
  transport: new FetchTransport(),
  middleware: [
    new AuthMiddleware(authProvider),
    new RetryMiddleware(),
  ],
})
```

📌 这样带来的好处：

* HttpClient **无业务知识**
* Auth 策略可替换
* 后端 / 前端 / SSR 复用同一套 http core

## 八、那“一个 Client 能不能连多个系统？”

**可以，但要“显式”**

### 推荐：工厂，而不是自动判断

```ts
export function createHttpClient(options: {
  auth: AuthProvider
  transport: HttpTransport
}) {
  return new HttpClient({
    transport: options.transport,
    middleware: [new AuthMiddleware(options.auth)],
  })
}
```

使用时：

```ts
export const internalClient = createHttpClient({
  auth: new SignatureAuthProvider(),
  transport: nodeTransport,
})

export const thirdPartyClient = createHttpClient({
  auth: new NoAuthProvider(),
  transport: nodeTransport,
})
```

---

## 九、总结一句非常工程化的话

> **不要让 HttpClient“变聪明”，要让“装配它的人足够明确”。**

* transport：启动期决定
* auth：策略注入
* middleware：只做流程，不做业务判断
* HttpClient：一旦创建，就是稳定、可预测的请求管道
