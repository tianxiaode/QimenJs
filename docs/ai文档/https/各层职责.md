> 1️⃣ 不再互相越权
> 2️⃣ 复杂度被限制在固定位置

# 一、http 模块的总体分层（先定大框）

你现在的 http 模块，本质应该只有 **四层**：

```
┌────────────────────────┐
│   应用层 / 仓储层       │  ❌ 不在 http 模块
└────────▲───────────────┘
         │
┌────────┴───────────────┐
│   HttpClient（门面）    │  ← 唯一对外 API
└────────▲───────────────┘
         │
┌────────┴───────────────┐
│   响应解析管道           │  ← 复杂性集中区
│   (Response Pipeline)   │
└────────▲───────────────┘
         │
┌────────┴───────────────┐
│ Transport / Fetch / XHR │  ← 纯 IO
└────────────────────────┘
```

**所有“五花八门”只能在中间那一层出现**，这是底线。

---

# 二、core 目录 ——「规则 & 抽象层」

> **原则：core 里没有任何浏览器 API、fetch、xhr、window**

### 1️⃣ `HttpClient.ts`

**职责（只能做这些）：**

* 作为 **http 模块唯一对外入口**
* 组合：

  * transport
  * response pipeline
  * middleware（请求前）
* 统一请求流程：

  ```
  build request
  → middleware
  → transport
  → response pipeline
  → return / throw
  ```

**绝对禁止：**

* ❌ 解析具体后端字段（code / msg）
* ❌ 判断业务成功失败
* ❌ 写 auth / token 逻辑
* ❌ 关心 json 结构

> HttpClient **不知道“成功”是什么**，只知道“请求完成”。

---

### 2️⃣ `HttpRequest.ts`

**职责：**

* 描述一个“已经标准化”的请求
* 包含：

  * url
  * method
  * headers
  * body
  * options（timeout / responseType / chunk）

**禁止：**

* ❌ 不做序列化
* ❌ 不拼接 token
* ❌ 不关心 transport

---

### 3️⃣ `HttpResponse.ts`

**职责：**

* 描述 transport 返回的**原始响应**
* 必须包含：

  * status
  * headers
  * rawBody（string | Blob | ReadableStream | null）

**关键原则：**

> HttpResponse **不等于“成功响应”**

**禁止：**

* ❌ 不抛异常
* ❌ 不解析 json
* ❌ 不判断 error

---

### 4️⃣ `HttpError.ts`

**职责：**

* http 模块内 **唯一错误类型**
* 用来承载：

  * 网络错误
  * 状态码错误
  * 后端错误（解析后）

**它是“容器”，不是“解释器”**

**禁止：**

* ❌ 不直接解析 response
* ❌ 不写 fromResponse(response)

> ❗ 你前面指出的 bug 正在这里：
> `HttpError.fromResponse` **应该被删除**

---

### 5️⃣ `RetryPolicy.ts`

**职责：**

* 只描述：

  * 是否重试
  * 重试间隔
  * 最大次数

**禁止：**

* ❌ 不关心错误类型细节
* ❌ 不关心 transport
* ❌ 不直接 sleep

---

### 6️⃣ `types.ts`

**职责：**

* 放 **跨文件共享的“稳定类型”**
* 例如：

  * HttpMethod
  * ResponseType
  * RequestOptions

**禁止：**

* ❌ 不放实现
* ❌ 不放业务枚举

---

# 三、transport 目录 ——「纯 IO 层」

> 这一层 **只解决“怎么发请求”**

### 1️⃣ `HttpTransport.ts`

**职责：**

* 抽象接口：

```ts
interface HttpTransport {
  send(req: HttpRequest): Promise<HttpResponse>
}
```

**禁止：**

* ❌ 不抛业务错误
* ❌ 不解析 body
* ❌ 不 retry

---

### 2️⃣ `FetchTransport.ts`

**职责：**

* fetch 的最薄封装
* 负责：

  * fetch
  * abort
  * 把 Response 转成 HttpResponse

**禁止：**

* ❌ 不 parse json
* ❌ 不处理 code
* ❌ 不判断成功失败

---

### 3️⃣ `XhrTransport.ts`

**职责：**

* 专门服务于：

  * 上传 / 下载进度
  * 分片
* 输出仍然是 HttpResponse

**禁止：**

* ❌ 不碰 error parser
* ❌ 不处理 chunk 逻辑（由上层控制）

---

### 4️⃣ `HeaderMiddleware.ts`

（这个名字其实不太好，但先按你现有的）

**职责：**

* transport 层的“技术性 header 注入”
* 如：

  * Content-Type
  * Accept

**禁止：**

* ❌ 不放 auth
* ❌ 不放业务 header

---

# 四、middleware 目录 ——「请求前加工」

> middleware **只作用于 request**

### 1️⃣ `AuthMiddleware.ts`

**职责：**

* 注入 token / cookie
* 从外部函数读取 token

**禁止：**

* ❌ 不 refresh token
* ❌ 不处理 401
* ❌ 不依赖 response

---

### 2️⃣ `RetryMiddleware.ts`

**职责：**

* 基于 RetryPolicy
* 捕获 transport 抛出的错误
* 决定是否再次 send

**禁止：**

* ❌ 不判断后端 code
* ❌ 不解析 response body

---

# 五、adapter 目录 ——⚠️ **建议删除**

你自己已经意识到这一点是对的。

### 为什么 adapter 在你这个架构里是多余的？

* 后端差异 **不只是接口形状**
* 还有：

  * 状态码规则
  * code 规则
  * data 包装
  * 错误字段
* adapter 很快会：

  * 一个后端一个 adapter
  * 逻辑复制
  * 难组合

👉 **你现在的 Response Pipeline 完全覆盖 adapter 的职责，而且更灵活**

# 六、真正承载复杂性的地方（你最关心的）

> **所有“五花八门”只允许出现在这里**

### ✅ Response Parser / Pipeline（你还没建文件夹，但这是核心）

它负责：

1. **无响应**

   * 网络错误
   * timeout
2. **状态码错误**

   * 但仍可能有 body
3. **body 类型判断**

   * blob / stream / text / json
4. **json 解析**
5. **错误判断**

   * code
   * success
   * msg
6. **数据提取**

   * data
   * result
   * payload

并且：

> **同一套逻辑同时适用于成功 & 失败响应**

这就是你之前说的“重叠复杂性”，**这里集中处理是唯一正确位置**。

# 七、最后给你一张「避坑速查表」

| 如果你想改…       | 正确位置                  |
| ------------ | --------------------- |
| 后端 code 不一样  | Response Parser       |
| 返回 data 包了一层 | Response Parser       |
| 200 里有错误     | Response Parser       |
| 下载进度         | XhrTransport          |
| retry 规则     | RetryPolicy           |
| token 注入     | AuthMiddleware        |
| 网络错误         | Transport → HttpError |
