这个问题你已经**踩到 HTTP 抽象里最容易翻车、但也最有价值的一层了**。
先给一个**明确结论**，然后告诉你**怎样既不分裂 Client、又不牺牲能力**。

---

## 先给结论（非常重要）

> ❌ **不需要两个 HttpClient**
> ❌ **也不应该让业务代码关心 XHR / fetch**
> ✅ **需要的是：一个 HttpClient + 多个 Transport + “能力选择”**

也就是说：
**Client 仍然只有一个**，
**Transport 在「请求级别」可选，但不是自动判断**。

---

## 一、为什么“进度 = 必须 XHR”这个判断是对的？

你说得完全正确：

### fetch 的硬限制

* ❌ 无上传进度（request body）
* ❌ 下载进度要读 stream，复杂 & 不稳定
* ❌ 某些浏览器对 ReadableStream 支持不一致

### XHR 的优势

* ✅ `onprogress`
* ✅ `upload.onprogress`
* ✅ 对文件上传 / 下载极友好

👉 **只要你要“可靠的进度条”，XHR 是唯一现实选择**

---

## 二、那为什么「两个 HttpClient」是坏味道？

```ts
uploadClient.post(...)
normalClient.get(...)
```

问题在于：

* auth / retry / header 重复
* 使用者要记住「用哪个」
* 一旦再加 SSE / AI stream，你会有第三个 Client

📌 **Client 数量爆炸是架构失控的前兆**

---

## 三、正确拆分点：Transport 是「能力」，不是「Client」

你现在的结构已经很接近正确答案了：

```
HttpClient
  └── HttpTransport
        ├── FetchTransport
        ├── XhrTransport
        └── （未来）StreamTransport
```

### 关键思想

> **HttpClient 不绑定 Transport 实现**
> **HttpRequest 决定“我需要什么能力”**

---

## 四、推荐的设计：Request-level Transport Hint（重点）

### 1️⃣ HttpRequest 声明能力需求

```ts
export interface HttpRequestOptions {
  onUploadProgress?: (e: ProgressEvent) => void
  onDownloadProgress?: (e: ProgressEvent) => void
  responseType?: 'json' | 'blob' | 'stream'
}
```

或者更明确一点：

```ts
export interface HttpCapabilities {
  uploadProgress?: boolean
  downloadProgress?: boolean
  streaming?: boolean
}
```

---

### 2️⃣ Transport 自己声明“我支持什么”

```ts
export interface HttpTransport {
  supports(cap: keyof HttpCapabilities): boolean
  send(req: HttpRequest): Promise<HttpResponse>
}
```

```ts
class FetchTransport implements HttpTransport {
  supports(cap) {
    return cap === 'streaming'
  }
}
```

```ts
class XhrTransport implements HttpTransport {
  supports(cap) {
    return cap === 'uploadProgress' || cap === 'downloadProgress'
  }
}
```

---

### 3️⃣ 在 Client 内部选择 Transport（不是业务代码）

```ts
class HttpClient {
  constructor(
    private transports: HttpTransport[],
  ) {}

  private pickTransport(req: HttpRequest) {
    const caps = req.capabilities()
    return this.transports.find(t =>
      caps.every(cap => t.supports(cap))
    )
  }
}
```

使用：

```ts
httpClient.post('/upload', file, {
  onUploadProgress: e => { ... }
})
```

📌 **业务层只表达“我要进度”**
📌 **HttpClient 负责找 XHR**

---

## 五、这样你只需要一个 Client

```ts
const httpClient = new HttpClient({
  transports: [
    new FetchTransport(),
    new XhrTransport(),
  ],
})
```

* 普通请求 → Fetch
* 上传 / 下载进度 → XHR
* 将来加 AI stream → StreamTransport

**Client 不变，能力扩展**

---

## 六、你提到的 AI 返回数据（非常关键）

> 估计因为要读 ai 返回的数据，还需要一个 FetchSource？

这个判断 **非常专业，而且是对的**。

### AI / SSE / LLM 返回的特点

* chunked
* streaming
* token-by-token
* fetch + ReadableStream 是正道
* XHR ❌ 不适合

### 这正好是第三种能力：

```ts
capabilities: {
  streaming: true
}
```

```ts
httpClient.post('/ai/chat', data, {
  responseType: 'stream',
})
```

→ 自动命中 `FetchTransport`

## 七、你最终会得到的能力矩阵

| 场景       | 能力                | Transport |
| -------- | ----------------- | --------- |
| 普通 API   | json              | Fetch     |
| 文件上传     | upload progress   | XHR       |
| 文件下载     | download progress | XHR       |
| AI / SSE | streaming         | Fetch     |
| 后端 Node  | stream            | NodeFetch |

**没有 Client 爆炸**
**没有 if/else**
**没有业务侵入**
