这个想法非常到位。**“规则先行”是架构设计的核心，特别是这种全线性流水线，必须明确“什么时候该停”以及“怎么停”**。

我们可以把这套规则总结为 **《全线性流水线执行公约》**，作为所有后续开发者的“交通法规”。

---

### 1. 流水线执行与中断公约

我们将中断分为两种：**“悲观中断（错误）”** 和 **“乐观中断（短路）”**。

#### A. 悲观中断：抛出异常 (Exception)

* **触发条件**：处理器执行过程中发生不可逆错误（如 401 未授权、校验失败）。
* **框架行为**：`FlowRunner` 使用 `try...catch` 捕获。
* **状态记录**：
* `ctx.control.isAborted = true`
* `ctx.control.interruptedBy = processor.id`
* `ctx.error = ErrorInstance`


* **后续影响**：执行立刻停止，进入全局错误处理。

#### B. 乐观中断：短路返回 (Short-circuit)

* **触发条件**：处理器逻辑已完成，无需后续处理（如 **命中缓存**、**Mock 模拟**）。
* **触发方式**：在处理器内部设置 `ctx.control.isHandled = true`。
* **状态记录**：同样记录 `interruptedBy`，以便追踪是从哪跳出的。
* **后续影响**：跳过后续所有处理器，直接返回当前 `ctx.data.result`。

---

### 2. `FlowContext` 的控制中心设计

为了支撑上述规则，`Context` 的控制字段需要这样设计：

```typescript
interface FlowControl {
    isAborted: boolean;      // 是否因为错误/取消而中断
    isHandled: boolean;      // 是否因为已处理完成而主动跳出
    interruptedBy?: string;  // 记录中断发生在哪一个 Processor ID
    signal: AbortSignal;     // 用于透传给底层 IO 的取消信号
}

```

---

### 3. `FlowRunner` 核心执行逻辑 (伪代码)

这是保证“方向”不乱的灵魂：

```typescript
class FlowRunner {
    static async run(ctx: FlowContext) {
        const pipeline = Registry.getPipeline(ctx.tag, ctx);

        try {
            for (const processor of pipeline) {
                // 1. 外部取消检查
                if (ctx.control.signal.aborted) {
                    ctx.control.isAborted = true;
                    break;
                }

                // 2. 状态监测：是否已被前置处理器短路
                if (ctx.control.isHandled) break;

                // 3. 执行处理器
                await processor.handler(ctx);

                // 4. 执行后检测：记录断点 ID
                if (ctx.control.isHandled) {
                    ctx.control.interruptedBy = processor.id;
                    break;
                }
            }
        } catch (err) {
            // 5. 悲观中断处理
            ctx.control.isAborted = true;
            ctx.control.interruptedBy = currentProcessorId; // 捕获当前的 ID
            ctx.error = err;
            throw err; // 继续向上传递或内部消化
        }

        return ctx.data.result;
    }
}

```

### 4. 补充规则（预防未来的坑）

除了中断逻辑，还有三个开发规则需要写进文档：

1. **原子性规则**：
* 一个处理器只做一件事（比如只管 Token，或者只管 URL）。如果逻辑太复杂，拆分成两个 `offset` 相邻的处理器。


2. **不可逆规则（针对 5000 权重以下）**：
* 一旦跨过 `CORE_IO (5000)`，后续处理器（Weight < 5000）**不得**再修改 `ctx.http` 下的任何参数。因为请求已经发出了，修改 URL 已经没有意义。


3. **幂等性建议**：
* 处理器应该尽量不依赖外部全局变量，所有的输入输出都应该在 `ctx` 内完成，确保流水线在重试时是安全的。



---

### 5. 巡检器的价值凸显

有了 `interruptedBy`，我们的巡检器就非常强大了。当一个请求没拿到结果时，你执行 `inspect`，它会告诉你：

> **"Request Interrupted at: [CacheProcessor] (Weight: 8500) Reason: Handled"**

你立刻就知道是因为缓存命中了，所以没发网络请求。
