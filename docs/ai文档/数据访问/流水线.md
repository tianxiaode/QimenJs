关于你提到的“删除确认”等逻辑，放在 `EntityAction` 流水线中处理是绝对正确的，这样 `EM` 就能保持纯粹的执行力。

### 1. `list` 标准流水线清单 (归类版)

我们可以将这些步骤对号入座到 `ActionCategory` 中，你会发现逻辑变得非常直观：

| 阶段 (Category) | 处理器 ID | 职责 (Description) | 归属建议 |
| --- | --- | --- | --- |
| **PREPARE** | `url-builder` | 结合 `DomainConfig` 和路径生成最终 URL | **Global** (通过模板解析) |
| **ENRICH** | `header-align` | 调用 `Domain.getHeaders()` 对齐请求头 | **Global** (通用调用) |
| **ENRICH** | `params-align` | **对齐参数**：分页、过滤条件对齐。 | **Domain/Custom** (常需替换) |
| **GUARD** | `confirm-guard` | 如 `delete` 动作前的“二次确认”弹窗拦截 | **Action-specific** |
| **IO** | `http-transport` | 真正的 `axios/fetch` 请求执行 | **Global** |
| **FALLBACK** | `transport-fail` | 你提到的 **TransportFailure** 故障拦截 | **Global** |
| **TRANSFORM** | `status-align` | 根据状态码更新 `context.success` | **Global** |
| **TRANSFORM** | `data-align` | **数据对齐**：根据 Schema 或自定义逻辑清洗数据 | **Custom** (替换默认) |
| **EFFECT** | `ctx-finalize` | 对齐上下文最终接口，供 UI 使用 | **Global** |

### 2. 关于“删除确认”的处理逻辑

**“删除确认”应该作为一个 `GUARD` 阶段的处理器。**

如果放在 `EM` 里，`EM` 就会耦合 UI 交互（弹窗）；如果放在 `EntityAction` 流水线里：

1. **可插拔**：某些后台静默删除可以不注册这个 `Action`。
2. **逻辑内聚**：

```typescript
// DeleteConfirmGuard (GUARD 阶段)
handler: async (ctx) => {
    if (ctx.action !== 'delete') return;
    const confirmed = await UI.confirm('确定要删除吗？');
    if (!confirmed) return 'skip'; // 终止流水线，后续 IO 不会执行
}

```

### 3. 如何处理“自定义替换默认”？

你提到的“数据对齐需要自定义替换默认”，这可以通过 **`PriorityWeight` (Stage + Offset)** 完美解决。

* **默认处理器**：设置 `offset: 0`。
* **自定义处理器**：设置 `offset: 10`。
* **逻辑实现**：在执行时，如果发现已经有高优先级的处理器完成了“对齐”标记，默认处理器就跳过。

```typescript
// 默认的数据对齐处理器 (TRANSFORM 阶段)
handler: async (ctx) => {
    if (ctx.state.isAligned) return; // 如果被自定义的抢先处理了，就跳过
    ctx.data = alignBySchema(ctx.raw, ctx.schema);
    ctx.state.isAligned = true;
}

```

### 4. 简化后的核心优势

1. **统一的模型**：无论是 `list`、`save` 还是 `delete`，都跑在同一套 `getPipeline` 逻辑下。
2. **Domain 无感**：`header-align` 只需要关心 `Registry.domain.get(ctx.domain).getHeaders()`，不需要写死阿里还是微信。
3. **UI 洁净**：UI 只需 `em.list()`。至于中间发生了地址对齐、Header 注入、还是故障拦截，UI 完全不需要关心。

### 5. 总结与建议

你梳理的这套“对齐”流程已经可以覆盖 95% 的业务场景了。

**你的下一个关键点是：** 定义 `FlowContext`。
为了让这些处理器能“对齐”数据，`ctx` 必须包含：

* `schema`: 拿到的 `ResolvedSchema`。
* `domainConfig`: 拿到的当前域配置。
* `state`: 一个运行时的状态位存储（例如 `isAligned`, `isTransportFailure`）。

**你想看看这样一个能支撑你上述流程的 `FlowContext` 结构定义吗？** 它是连接这些处理器的“接力棒”。
