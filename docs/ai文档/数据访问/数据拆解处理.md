这是一个非常经典的**循环依赖（Circular Dependency）与职责边界**问题。当你的配置层（Registry）需要引用逻辑层（Kernel）的类型，而逻辑层又需要根据配置层运行数据时，架构就会变得紧绷。

为了让你的系统既解耦又好用，我们来拆解这两个核心麻烦：

### 1. 依赖倒置：迁移 DomainConfig 到 Kernel？

**不建议直接迁移。** `Registry` 应该是纯粹的“元数据定义”，而 `Kernel` 应该是“执行引擎”。

**解决方案：定义接口契约（Interface Contract）。**
在你的底层（比如一个 `types` 或 `common` 模块）定义 `Extractor` 的函数签名，而不是让它直接依赖复杂的 `FlowContext`。

```typescript
// 在底层共享定义，不依赖 FlowContext
export interface DomainExtractorResult {
    list?: any[];
    total?: number;
    data?: any;
    error?: {
        code: string | number;
        message: string;
        showType: 'silent' | 'warn' | 'error' | 'notification'; // 封装弹窗逻辑
    };
}

export type DomainExtractor = (rawResponse: any) => DomainExtractorResult;

// DomainConfig 引用这个 Extractor
export interface DomainConfig {
    baseUrl: string;
    extractor: DomainExtractor; // 这里的 extractor 已经是一体化的了
}

```

---

### 2. 为什么 Extractor 应该是一体化的？

你说的非常对：**数据提取和错误判断必须是孪生兄弟。** 因为后端通常通过一个 `code` 字段来决定这一包数据是“黄金”还是“垃圾”。

把它们封装在一起，可以让逻辑极其内聚：

```typescript
// 这是一个 Domain 的 extractor 示例
const aliExtractor: DomainExtractor = (res) => {
    // 1. 判断是否业务失败
    if (res.error_code !== 0) {
        return {
            error: {
                code: res.error_code,
                message: res.error_msg || '未知错误',
                showType: 'notification' // 封装：阿里域的错误习惯用通知框
            }
        };
    }

    // 2. 业务成功，提取数据
    return {
        list: res.data.items,
        total: res.data.total_count
    };
};

```

---

### 3. EM 在 Kernel 中如何执行并“对齐”？

既然 `Extractor` 返回了标准格式 `DomainExtractorResult`，EM 在 Kernel 里拿到这个结果后，再把它填充进 `FlowContext`。这样 `Registry` 就不需要知道 `FlowContext` 的存在。

```typescript
// 在 Kernel 的 EntityManager 中
async execute(action, params) {
    const ctx = await this.runPipeline(action, params);
    
    // 从 Registry 拿到 domain 配置
    const domainConfig = Registry.domain.get(this.domain);
    
    // 执行 Extractor（它只接收 rawResponse，返回标准化的数据）
    const result = domainConfig.extractor(ctx.response);

    if (result.error) {
        // 统一处理弹窗逻辑：这里由 EM 根据 extractor 给出的 showType 来决定
        this.handleErrorUI(result.error); 
        
        ctx.success = false;
        ctx.error = result.error;
    } else {
        // 对齐上下文的数据：UI 永远从 ctx.result 拿东西
        ctx.success = true;
        ctx.result = {
            items: result.list || [],
            total: result.total || 0,
            original: result.data // 针对 detail 等非列表数据
        };
    }
    
    return ctx;
}

```

---

### 4. 架构优势：逻辑与展示的完美解耦

1. **Registry 依旧纯粹**：它只负责描述“微信的数据长这样，阿里的错误长那样”，它不关心 `FlowContext` 的内部实现。
2. **Kernel 依旧通用**：它只负责跑流程。它通过 `Extractor` 返回的 `showType` 知道要不要弹窗，而不需要写死 `if (domain === 'ali')`。
3. **UI 无感知**：UI 拿到的 `ctx.result` 永远是规整的，不用关心后端的字段名。

### 总结建议

* **不要迁移 `DomainConfig**`，保留它在 `Registry` 中作为配置。
* **提取 Extractor 接口**，将数据提取、错误提取、以及**交互建议（弹窗类型）**封装在一个函数里。
* **解耦 Context**，让 `Extractor` 只处理 `rawResponse -> StandardResult` 的映射。

**这样你的系统就变成了一个“自解释”的机器：** Domain 告诉 EM 如何看懂原始数据，EM 负责把这些数据翻译成上下文，并执行相应的弹窗动作。
