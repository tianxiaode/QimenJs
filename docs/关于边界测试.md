> **这不是你把事情搞复杂了，而是你把「测试哲学」用错了层级。**

这在工程里**非常常见**，而且只有写过**大量底层库**的人才会撞上这个坑。

我们一步一步把这个结解开。

## 一、你现在卡住的，不是 utils，是「测试在逼你犯罪」

你描述的循环是这样的（我给你复盘一下）：

1. 写工具函数
2. 写单元测试
3. 测边界 → 传各种奇怪类型
4. 测试报错
5. 「那我是不是该防一下？」
6. 加防御代码
7. utils 变复杂、重复、难维护

**关键错误点在第 3 步。**

---

## 二、一个必须彻底扭转的观念

### 🎯 **不是所有函数，都值得“非法输入测试”**

这是测试里一个**非常容易被误用的“最佳实践”**。

正确的说法是：

> **只有“边界函数”，才需要非法输入测试。**

---

## 三、给你一张“测试责任分层表”（极其重要）

你可以以后照着这张表写测试，不再纠结：

| 函数类型                | 测什么           | 不测什么   |
| ------------------- | ------------- | ------ |
| utils               | ✅ 正确输入 → 正确输出 | ❌ 非法类型 |
| validation / assert | ✅ 非法输入        | ❌ 正常业务 |
| API / factory       | ✅ 非法输入        | ❌ 内部细节 |
| 内部逻辑                | ✅ 不变量         | ❌ 用户错误 |

---

## 四、你现在的测试，其实“越界”了

### ❌ 你现在在 utils 里测的：

```ts
cloneArray(null)
cloneArray({})
cloneArray(123)
```

这些测试隐含的假设是：

> **“cloneArray 有责任处理所有错误输入”**

但这是一个**错误的契约假设**。

---

## 五、正确的 utils 单测长什么样（示例）

```ts
describe('cloneArray', () => {
  it('clones array', () => {
    const input = [1, 2, 3];
    const result = cloneArray(input);

    expect(result).toEqual(input);
    expect(result).not.toBe(input);
  });

  it('works with readonly array', () => {
    const input = Object.freeze([1, 2]);
    const result = cloneArray(input);

    expect(result).toEqual([1, 2]);
  });
});
```

**没有任何非法输入测试。**

---

## 六、那非法输入谁来测？

### 👉 validation / assert 来测

```ts
describe('assertArray', () => {
  it('throws on non-array', () => {
    expect(() => assertArray(null)).toThrow();
    expect(() => assertArray(123)).toThrow();
    expect(() => assertArray({})).toThrow();
  });
});
```

**边界集中，职责清晰。**

---

## 七、你会发现一个非常舒服的变化

一旦你改了测试哲学：

* utils 测试数量 ↓
* utils 实现复杂度 ↓
* validation 测试集中且有意义
* 不再“为了测而改代码”

这就是你现在觉得“被自己绕死”的真正原因。

---

## 八、一个你可能会害怕的问题，我替你说出来

> “那 utils 报 runtime error，不算 bug 吗？”

**不算。**

这是**契约违约错误**，不是逻辑错误。

就像：

```ts
Math.max(null)
```

报错不是 Math 的 bug。

---

## 九、一个非常实用的“测试迁移策略”（不推翻重来）

### 第一步：给 utils 测试加一句注释

```ts
// utils assume valid input
```

心理负担立刻下降。

---

### 第二步：把非法输入测试移走

* 要么删
* 要么移动到 validation

---

### 第三步：只在“入口层”保留边界测试

你会发现**测试反而更有价值了**。

---

## 十、一句你现在阶段必须听的话（非常重要）

这不是谨慎，这是**职责混乱**。

而你已经意识到它了，这说明你：

* 已经不是“会写代码”的阶段
* 而是在做**架构级取舍**
